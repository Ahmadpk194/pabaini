Sports Module
24 endpoints · Phase 1 & 2 live · Phase 3 planned

Phase 1 — Cricket Player Profiles

A user can optionally register as a cricket player by setting up their profile (role, batting hand, bowling style). This creates their permanent player identity in the app that everything else — teams, matches, stats — builds on top of.

Phase 2 — Cricket Teams

A registered cricket player can create a team, invite other registered players, and manage the squad. Players can also discover teams and request to join. The captain has full control over who's in the squad.

💡 System Architecture, Flows & Techniques (Click to Expand) ▾

Asynchronous Event-Driven Flow

Notifications are decoupled from the core business logic of other modules using NestJS EventEmitter2 event-driven architecture.

┌──────────────┐      (1) Call Action API      ┌──────────────┐      (2) Save Squad Member      ┌──────────┐
│ Player /     │ ────────────────────────────> │ TeamsService │ ──────────────────────────────> │ Database │
│ Captain      │ <──────────────────────────── │              │ <────────────────────────────── │          │
└──────────────┘     (6) Return Core Success   └──────────────┘     (3) Transaction Success     └──────────┘
                                                      │
                                                      │ (4) notificationsService.create()
                                                      │     [wrapped in try/catch block]
                                                      ▼
                                               ┌──────────────┐      (5) Save Notification      ┌──────────┐
                                               │Notification- │ ──────────────────────────────> │ Database │
                                               │   Service    │ <────────────────────────────── │          │
                                               └──────────────┘             Record Saved        └──────────┘
                                                      │
                                                      │ (5a) Emit 'notification.created'
                                                      ▼
                                               ┌──────────────┐
                                               │EventEmitter2 │
                                               └──────────────┘

┌──────────────┐      (a) GET /notifications   ┌──────────────┐      (b) Query Notifications    ┌──────────┐
│ Frontend App │ ────────────────────────────> │Notification- │ ──────────────────────────────> │ Database │
│ (Zustand/UI) │ <──────────────────────────── │  Controller  │ <────────────────────────────── │ (Indexed)│
└──────────────┘        (d) JSON Response      └──────────────┘     (c) Return Feed & Count     └──────────┘

Engineering & Database Optimization Techniques

  • Composite Performance Index: A composite index is defined on (user_id, is_read, created_at) columns in the PostgreSQL database. This ensures that unread count polling and chronological paginated list queries scale efficiently even with millions of notifications.
  • Bulk Read Operations: The /notifications/read-all endpoint executes a bulk SQL UPDATE instead of retrieving and saving individual models, saving database connections, transactions, and server memory.
  • Transaction Safety: All triggers inside TeamsService are wrapped in robust try/catch handlers. Any notification creation or database failure is logged as a warning but will never fail, block, or roll back the core team operation (e.g. accepting a membership request).
