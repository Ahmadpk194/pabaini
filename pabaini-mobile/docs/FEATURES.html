Pabaini Mobile - Complete Features Documentation

This document provides a comprehensive overview of all features implemented in the Pabaini mobile application, covering core authentication, onboarding, announcements feed, moderation actions, and peripheral directories.

🔑 1. Authentication & Registration (app/(auth)/login.tsx)

Objective: Authenticate and dynamically register village members securely using Firebase Auth.

  • Phone Number OTP Auth:
  • Accepts the user's phone number, sends a verification code via SMS, and renders a 6-digit OTP verification field.
  • Implements a visual Resend Code countdown timer (preventing request flooding).
  • Google Sign-In:
  • Provides a simple one-click authentication alternative for Google accounts.
  • Dynamic Registration:
  • On successful authentication, the Firebase ID token is forwarded to the NestJS backend via POST /auth/login. If the user does not exist in the database, a record is automatically initialized.

    • 📱 2. Post-Login Onboarding Flow (app/(onboarding)/profile-setup.tsx)

    Objective: Ensure newly registered users complete essential profile data before viewing the notice board.

  • Redirection Gate (app/index.tsx):
  • Verifies if a logged-in user has a valid name. If empty, automatically routes them to the profile setup screen, blocking feed access.
  • Setup Form:
  • Avatar Upload: Integrates expo-image-picker to select profile pictures from the camera roll or capture one live.
  • Diaspora Status: Toggle switch indicating whether the user lives abroad (which adds a diaspora label to their posts).
  • Read-Only Village: Shows the default village setting ("Pabaini").
  • Initials Generator: Automatically draws initials inside a placeholder circle if no photo is uploaded.
  • Validation: Restricts name length between 3 and 50 characters, showing loading indicators during sequential uploads and patches.

    • ⚙️ 4. Announcement Moderation Drawer (Pin & Delete Modal)

    Objective: Context-specific administrative actions overlaying announcement cards.

  • Three-Dots Trigger: Renders an ellipsis icon on notice card headers, gatekept to show only to the post author or admins/moderators.
  • Custom Bottom Sheet Modal: Built with native <Modal> (sliding from the bottom over a translucent backdrop) to maintain high performance with zero third-party dependencies.
  • Security Access Rules:
  • Pin/Unpin: Restrained to Admin and Moderator roles. Updates pinned state on backend.
  • Delete: Restrained strictly to the Author and Admins. Triggers confirmation pop-up and executes a soft delete (marking is_deleted = true in the DB while keeping storage media for records).
  • Separate Action Loaders: Employs an activeAction state so that spinner animations activate only on the pressed item, keeping all controls disabled during api calls.

  • Header Bar: Features Cancel (left) + "New Announcement" (center) + loading-capable Post (right). Disabled if title is under 3 characters or content is under 10.
  • Image Attachment: Attaches a high-quality picture using expo-image-picker, rendering a full-width preview with a close (X) overlay.

  • Captain Match Result Flow:
  • When navigated to with a ?matchId=<id> query parameter (from the Match Details screen), the screen automatically fetches the match and:
  • Sets the category to match_result.
  • Pre-fills the title with "Match Update: Team A vs Team B".
  • Pre-fills the content with a generated result summary (winner, final score).
  • The access guard is bypassed for the authenticated captain of either team in the referenced match. All other users continue to be blocked unless they are Admin or Moderator.
  • Gatekeeping: Routes return Access Denied if a standard resident (not a team captain) attempts to load the creation page without a valid match context.

    • 💬 7. Announcement Comments Integration (app/announcement/[id].tsx)

    Objective: Enable community discussion, feedback, and interactive moderation of announcements.

  • Paginated Listing: Fetches and renders announcement comments oldest first.
  • Loading & Empty States: Displays an inline loading indicator while comments load. Shows a friendly placeholder ("No comments yet. Be the first to comment.") if there are no comments.
  • Embedded Match Card: If the announcement has a match_id set, a live MatchCard is rendered below the post content in the detail view, showing the referenced match's current status, scores, and a tap-to-navigate link.
  • Optimistic Creation Flow: Inserts new comments into the UI immediately with a temporary ID and 0.6 opacity (isPending: true), sending the API request in the background. On success, the local comment is replaced by the server response; on failure, the comment is removed and a native alert error message is shown.
  • Inline Edit Flow: Authorized owners (where canEdit is true) can tap "Edit" next to the timestamp, which loads the text into the input field and displays an editing banner with a "Cancel" button.
  • Soft Deletion Flow: Gated by canDelete: true. Displays a confirmation prompt before calling the deletion API, immediately removing the comment from the screen and decrementing parent announcement badges.

    🔐 12. Guest Mode & Authentication Gating

    Objective: Allow guest (unauthenticated) users to browse announcements and sports matches while restricting access to gated pages and action triggers to avoid client and server errors.

  • Restricted Navigation Zone:
  • Guests are limited to two screens: Announcements Feed (Home) and the Matches tab under Sports.
  • The top tabs for Players, Teams, and Leaders on the Sports hub are hidden entirely for guests, rendering only the Matches ScrollView.
  • Visiting gated routes directly (e.g., Roster, Create Team, Match setup, Scoring, Notifications, Resident profiles) redirects to the custom LoginRequiredGate component.
  • Action Intercepting Overlay:
  • Interactive write triggers (such as Liking a notice, Commenting, Registering as a player, or Joining a team squad) are intercepted by the global LoginPromptModal which requests user authentication.
  • Auth State & Cache Clearing:
  • Logouts and guest transitions flush all Zustand persistent stores (sportsStore, teamsStore, notificationsStore) and trigger a full TanStack Query client clear (queryClient.clear()) to prevent data leaking.
  • Bypassing Auth Headers:
  • On the frontend, the Axios request interceptor checks is_guest in SecureStore and skips Firebase token acquisition.

    • 🔐 15. Safe Navigation Architecture

    Objective: Protect the app's routing stack from rapid double-tapping (which pushes the same screen multiple times) and duplicate route pushes (which push a route matching the current path).

  • Problem: In high-traffic lists or interactive cards (e.g. tapping notice cards, post creators, profile links, or buttons), rapid consecutive user taps push the same screen multiple times onto the navigation stack. Going back requires pressing the back button once for every extra tap.
  • Centralized Solution:
  • Module-level Navigation Lock: Created safeNavigation.ts with safeRouterPush and safeRouterReplace wrappers. On execution, it sets a global isNavigating flag that blocks subsequent navigation calls for a 500ms self-healing lock window.
  • Duplicate Path Interception: Compares the target path against a globalCurrentPath tracker. If they match (excluding query parameters), the navigation push is safely blocked.
  • Reactive Path Tracker: Implemented a <PathnameTracker /> in the root layout (_layout.tsx) that reads usePathname() and updates the navigation utility dynamically.
  • Migrated Areas:
  • Home Notice Feed: FAB Post button, Notification Bell, Search Icon, and AnnouncementCard elements (Notice click, Comments click, Author avatar press).
  • Global Search: Detail clicks for Users, Players, and Teams.
  • Notification Rows: Deep-link row click navigations.
  • Sports Dashboard & Directories: Bell press, Register Player buttons, player profiles, See All players list, discover teams list, empty state team creators, challenge request buttons, and match detail card lists.

Persisted to AsyncStorage under the key pabaini-theme.

    2. ThemeContext update (src/context/ThemeContext.tsx): Refactored to read colorScheme from useThemeStore instead of local useState. Resolution logic: 'system' → follows device useColorScheme() live; 'light' or 'dark' → forces that mode.     🏏 19. Sports — Batsman Retirement (Retired Hurt / Retired Out) (app/sports/cricket/matches/[id]/score.tsx)

    Objective: Allow the scorer to retire an active batsman under two cricket-rule-compliant outcomes during live scoring, without disrupting the rest of the innings flow.

  • Two Distinct Retirement Outcomes:
  • Retired Hurt — Batsman temporarily leaves the field due to injury. Their stats (runs, balls, 4s, 6s) are frozen and preserved. The innings record stays open (is_not_out = true), meaning they are not counted as a wicket and do not appear in the fall-of-wickets table. A retired-hurt batsman can return to bat later in the same innings when selected as the next incoming batsman.
  • Retired Out — Batsman permanently leaves. This counts as a full team wicket (increments wickets tally, appears in fall-of-wickets), but the bowler does not receive wicket credit for either type of retirement.
  • Retirement Action via Partnership Drawer:
  • To keep the main scoring console clean and uncluttered, the retirement action is placed inside the Partnership Details bottom drawer, which opens when the scorer taps the active batsmen card.
  • Inside the drawer, a small red-tinted "Retire" button appears next to each active batsman (striker and non-striker) alongside their current run/ball count.
  • Tapping "Retire" dismisses the drawer and immediately presents a native Alert dialog asking the scorer to choose between Retired Hurt and Retired Out.
  • Dedicated Batsman Retirement Endpoint:
  • Batsman retirement now operates through a dedicated PATCH /sports/cricket/matches/:id/batsman/retire endpoint rather than recording a fake ball delivery.
  • This ensures that batsman retirement does not increment the current over's ball count, trigger over rollovers, or affect the bowler's runs conceded or overs bowled.
  • The endpoint accepts a target field ('striker' or 'non_striker'), allowing the non-striker to be retired directly without requiring strike rotation.
  • Wicket Modal Updates:
  • The Wicket modal (used for both normal dismissals and retirements) shows retired_hurt and retired_out as selectable dismissal types in the type picker.
  • The modal title dynamically changes to "Retire Batsman" when a retirement type is selected, and shows the name of the player being retired.
  • The "Next Batsman" picker section is shown whenever there are available squad players to replace the retiring batsman.
  • Returning Batsmen in Next-Batsman Picker:
  • The next batsman sub-modal is grouped into two sections:
  • Returning Batsmen (Retired Hurt) — Players who previously retired hurt and can return. Each entry displays their frozen stat line (e.g., "Resuming at 14 (9b)").
  • New Batsmen (Not Batted) — Players who have not yet come to bat this innings.
  • Scorecard & Live Display:
  • In the live spectator view (live.tsx), dismissal labels are rendered with spaces (e.g., "retired hurt", "retired out").
  • Since retirement is not a ball bowled, it does not write a ball event. For legacy/historical events, retired_hurt displays as a soft amber badge with "RH" (or "RO" for retired out) instead of a red "W" badge in over circles, and shows "Retired Hurt" in commentary lines instead of "WICKET!".
